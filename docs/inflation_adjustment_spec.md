# Inflation adjustment: build spec

**What this builds.** A clean panel of consumer price index **levels**, keyed
`province × item_group × month`, plus the crosswalk that maps survey item names onto
`item_group`. Downstream code forms every ratio it needs from these levels.

**What this does not build.** No inflation factors, no ratios, no `(1+π)`, no
aggregation to case or municipality, no application to any weight. Those exist — in
`07_cpi_factor.do` and `24_inflate_to_psps_month.do` — but not here. See
[§7](#7-out-of-scope-for-this-step--and-where-each-piece-lives-instead) for the map.

Companion reading: `docs/conversion_factor_methodology.md` (the methodology this
feeds). This spec is self-contained for implementation purposes.

## 1. Why an inflation adjustment exists at all

PSPS households reported food quantities in non-standard units — "1 bilog of
carrot", "2 tumpok of prawns". The NSU Market Survey went to markets in
**2026m3–2026m5** and weighed those units so the quantities can be converted to
grams. PSPS itself was fielded **2023m12–2025m1**. The two sit in different price
rounds, roughly one to two years apart.

That gap only matters for one of the three weighing approaches.

| approach | what was measured | does the weight depend on the price level? |
|---|---|---|
| size-based (78% of cases) | enumerator asked for a small / medium / large unit and weighed it | **No.** A medium mango's grams are a property of the object. No money changed hands. |
| conventional (6%) | a traditional local unit (ganta, salop) | **No.** Same reasoning. |
| price-quantity (16%) | vendor's item weighed **at a preloaded reference price point** | **Yes.** A fixed peso amount buys less when prices are higher. |

Only the third row needs adjusting, and the adjustment lands on the **weight**, not
the price — the peso figure was preloaded into the form and could not be altered by
the enumerator, so it is the grams that flexed. Full argument in
`conversion_factor_methodology.md`, section "Why the adjustment sits on the weight".

### Why π cannot simply be set to zero

Measured over PSPS 2024m5 → MS 2026m4 on the PSA province × COICOP food CPI:

- Median correction **+7.4%**, range **−18.1% to +58.1%**. Field weights are
  recorded to the whole gram, so on a 200 g unit the median correction is ~15 g
  against 1 g of rounding.
- **Six of sixteen groups moved the other way** (rice −6.8%, fresh meat −4.0%, other
  meat −2.9%, sugar −2.4%, ice cream −1.9%, water ≈ 0), and signs flip *within* a
  group across provinces — leafy vegetables −9.4% in Iloilo, +58.1% in Antique. No
  single scalar can stand in for π.
- Because the sign is known per province × group, setting π to zero is not neutral
  noise; it biases every affected household in one direction, differing by item.

## 2. The deliverable

One table:

```
province × item_group × month  →  cpi, cpi_ma3, cpi_source
```

| column | meaning |
|---|---|
| `province` | UPPERCASE (`AKLAN`, `ILOILO`, …) |
| `item_group` | COICOP food group code as published by PSA |
| `mdate` | Stata monthly date |
| `cpi` | the index **level**, as published |
| `cpi_ma3` | 3-month centred moving average of the level |
| `cpi_source` | which coverage tier supplied the row (see §5) |

Plus the item crosswalk `(province, cons_name) → item_group` as a separate output.

### Why levels and not ratios

A CPI level is a fact about a province, a group and a month. A ratio is a level plus
a decision about which two months to divide. Shipping levels puts every such decision
downstream, where it can be revised without rebuilding the panel — and it keeps this
table usable by consumers that want a different pairing than the one the pipeline
happens to use.

That freedom was immediately worth having. The original design used the levels
**twice**: once to restate every market-survey weighing from its own month into a
common reference month so the market survey was internally comparable, and once to
carry that reference-month figure back to a household's PSPS interview month.

**The first of those is retired** (issue #29). The market survey visits any one
municipality within a few months, so restating across market-survey months averaged
across municipalities rather than removing a real price difference. The column that
carried it, `w_ref = corrected_weight * cpi_factor`, is gone. See the header of
`dofiles/00_shared/07_cpi_factor.do`, which explains why that file still exists
without it.

**One ratio remains**, and the pipeline builds it from these levels:

```stata
cpi_factor = cpi_at_m_ms / cpi_at_ref        // 07_cpi_factor.do, price-quantity rows only
```

with `REF = 2026m4`, the modal market-survey month. `cpi_factor` is exactly 1 on the
size-based and conventional branches by construction, because no money changed hands
in those weighings and there is nothing for an index to adjust.

This is the design argument working as intended: retiring half the original plan
changed nothing in this table. Had it shipped ratios, the retirement would have been
a rebuild.

## 4. Build steps

### 4.1 Import and normalize

Following `analysis.do:35–51`:

- `geolocation` → `province`, then **`strupper`**. The CPI file says `Aklan`;
  everything downstream uses `AKLAN`.
- `commodity` → `item_group`.
- `mdate = ym(year, month)`, format `%tm`. Drop `date`, `year`, `month`.

### 4.2 The item crosswalk join

> **Join on `(province, cons_name)`. Never on `cons_name` alone.**

The crosswalk is `isid cons_name province`: 95 rows, 19 unique `cons_name`. Exactly
one item's group varies by province — **ice cream**, because Iloilo has no CPI series
for it and falls back to the parent sweets/confectionery category. A `merge m:1
cons_name` against this file is an r(459).

Apply the same name normalization `analysis.do` does:

```stata
replace cons_name = "Drinks at restaurant, hotel, cafe, or kiosk" if strpos(cons_name, "restaurant") > 0
replace cons_name = subinstr(cons_name, "café", "cafe", .)
```

### 4.3 `cpi_ma3`

A 3-month centred moving average of the **level** (never of a ratio). Motivation:
individual series are violently volatile. Among the series this panel actually
carries, the largest single-month moves are Aklan *other vegetables* **+37.6%**
(2025m8), Aklan *tubers and plantains* **+35.4%** (2025m8), and Antique *other
vegetables* **+24.3%** (2025m12) immediately followed by **−20.0%** (2026m1) — a
spike-and-reversion pair that is exactly what a centred average is meant to absorb.

> Earlier drafts cited "green leguminous vegetables +77%". That series
> (`01.1.7.3`) exists in the source CSV but **no survey item maps to it**, so it
> never enters any calculation here. Do not use it as a motivating figure.

Handle series endpoints explicitly and **document the choice** (leave missing, or
shrink the window). Do not let the decision be implicit in whatever the function
defaults to.

> **Settled: endpoints are left missing.** The first and last month of every series
> get missing `cpi_ma3`, not a shrunk 2-point window — a 2-point average is a
> different estimator wearing the same column name, and silently mixing the two
> across a panel is worse than a gap a consumer can see. `06_cpi_panel.do:748–751`
> states the rule; line 1017 asserts the count, which is derivable from the panel's
> own shape (2 per series × 75 series = 150 of 2,250 rows).

Any consumer of `cpi_ma3` must therefore handle missing at 2023m12 and 2026m5.
`07_cpi_factor.do` checks for this explicitly before using `cpi_factor_ma3` as its
robustness variant.

## 5. Coverage ladder

Emit `cpi_source` recording which tier supplied each row:

| tier | source |
|---|---|
| 1 | province × exact COICOP group |
| 2 | province × parent COICOP group |
| 3 | national × group |
| 4 | all-food |

Report counts per tier. Coverage is *believed* complete for 5 provinces × 16 groups,
so tiers 2–4 may come back empty — **confirm this empirically and say so either
way** rather than assuming.

Do not silently drop unmatched rows. List every `(province, item_group, month)` that
a survey item maps to but the CPI file lacks.

> **Settled on the pinned vintage: tier 1 covers everything.**
>
> | tier | rows |
> |---|---|
> | 1 — province × exact COICOP group | 2,250 |
> | 2 — province × parent group | 0 |
> | 3 — national × group | 0 |
> | 4 — all-food | 0 |
> | unresolved | 0 |
>
> Tiers 2–4 were confirmed empty, not merely assumed. The ladder is kept in the code
> anyway: it costs nothing on a vintage that does not need it, and a future vintage
> that drops a series would otherwise fail silently or halt the build.
>
> The panel is 2,250 rows and not 2,400 because 75 of the 80 possible
> `(province, item_group)` pairs exist. The 5 absent pairs are the ice-cream
> exception of §4.2 — Iloilo maps that item to the parent sweets/confectionery group,
> so the two groups each cover a subset of provinces. That is a property of the
> crosswalk, not a coverage gap. Every included pair carries all 30 months.

## 6. Known traps

These are verified, not hypothetical.

1. **`archive/analysis.do:535`** runs `merge m:1 cons_name using coicop_item_crosswalk`
   — the bug §4.2 warns about. Do not copy it.
2. **`archive/analysis.do` does not run to completion**, and did not before it was
   archived. Line 537 is a bare `merge` with no arguments. Lines 37–210 are sound;
   do not assume the file executes.
3. **`archive/analysis.do:204`** uses `assert(2 3) keep(3)`. The `assert(2 3)` means an
   unmatched household *halts* rather than being dropped — so this is not a silent
   drop, contrary to what one might assume from `keep(3)` alone.
4. `cap` and `cap rename` **silence failures**. Verify after any batch of them.
5. Before recoding any coded variable, inspect its actual coding (`label list`,
   `tab var, m`, `describe`). Never infer a scheme from a sibling variable. Treat
   `(0 real changes made)` on a mapping line as a red flag, not noise.

## 7. Out of scope for this step — and where each piece lives instead

The boundary is the point of the design (§2): this step ships levels, and every
decision about *which two levels to divide* sits downstream. So none of the
following belongs in `06_cpi_panel.do`. All of them now exist elsewhere.

| kept out of this step | where it lives |
|---|---|
| ratios, inflation factors, `(1+π)` | `00_shared/07_cpi_factor.do` — builds `cpi_factor` and `cpi_factor_ma3` |
| choosing which rows qualify for adjustment | `07_cpi_factor.do` — drops the 98 price-quantity rows whose recorded price was not the price handed over, and sets `cpi_factor = 1` on the size-based and conventional branches |
| applying anything to a weight | `20_psps_retrofitting/24_inflate_to_psps_month.do` |
| aggregating to case or municipality | the outcome builds; municipality never enters the index itself (see the note below) |
| plotting the panel | `90_diagnostics/plot_cpi_inflation.py` |

**If you are editing `06_cpi_panel.do` and find yourself dividing one CPI by
another, stop.** That is the one rule here that is still a prohibition rather than a
signpost. The panel's value is that it is decision-free.

### Note on municipality

Municipality is deliberately absent from the key. PSA publishes at province level.
Municipality enters the pipeline only through which households sit where, via each
household's own interview month — never through the index itself.

## 8. Validation to report

- panel dimensions: provinces × item_groups × months; is it balanced; list gaps
- `cpi` distribution: min / p25 / p50 / p75 / max; assert none missing, zero, or
  negative
- counts per `cpi_source` tier
- top 10 largest month-on-month moves with province / group / month — a check that
  the volatility in §4.3 is real and not a parsing artefact
- **index integrity for ratio use**: confirm the series are fixed-base *levels*, not
  year-on-year rates, and check for a base break at the 2026 boundary. Prior work
  found median m/m change +1.3% at 2025m12→2026m1 vs +0.0% elsewhere, i.e. no break
  — verify this independently rather than taking it on trust.

  > **Settled: no base break.** Independently reproduced — median m/m change
  > **+1.22%** at 2025m12→2026m1 (n=75) against **+0.00%** at all other transitions
  > (n=2,100). The boundary move is in line with a typical month, so the levels can
  > be divided across it. Observed range 83.1 to 263.1, centred near 100 — a
  > fixed-base level, not a growth rate, which would sit near 0.
- how far `cpi_ma3` departs from `cpi`, by group
- the full sha256 of the vintage used

## 9. Environment

- Stata: `"C:\Program Files\StataNow19\StataSE-64.exe" -e do <file>`. Always a
  **fresh isolated batch process**. Never kill Stata by image name — only a PID you
  spawned yourself. Do **not** use `C:\Program Files\Stata17` (expired licence).
  `-e` writes `<dofile>.log`; a static log does not mean the process is hung.
- **No nested `preserve`** in Stata — that is r(621). Use a tempfile `save`/`use`
  round trip to restore state instead.
- The build is a do-file, not Python — project policy (`CLAUDE.md`) reserves Python
  for fuzzy string matching, `.xlsx` I/O and unicode normalization, and this step
  does none of them. The Python original is retired to `dofiles/archive/`.
- Verify magnitudes, not just structure. "Ran without error" is not "correct".

## 10. Rebuilding the panel

```bash
"C:\Program Files\StataNow19\StataSE-64.exe" -e do 00_shared\06_cpi_panel.do
```

Run it from `dofiles/`. It is called by nothing — it sits above both outcome
pipelines because the crosswalk and the CPI panel change only when their inputs
change. It overwrites all three files in `outputs/tables/` and regenerates
`cpi_panel_validation.txt` from scratch, so the report always describes the panel
sitting next to it.

**Read the validation report after every run**, and check the sha256 line first: the
build halts if the CPI file's hash does not match the vintage pinned in §3.1, which
is how a silent vintage swap surfaces.

The three files in `outputs/tables/` are tracked in git and read directly by
`07_cpi_factor.do`. They are deliverables, not scratch.
